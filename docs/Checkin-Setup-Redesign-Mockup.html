Setup, before anyone reaches the door

Three screens stand between an unboxed tablet and a working entrance: pair it, load tonight's guest list, sign in. They are the screens staff meet first and understand least — and the pairing screen is the least finished thing in the app.

This is a mockup, not shipped UI. No Kotlin has been written for it. Colours, type and control shapes are taken from the app's real theme files, so what you see is what the tablet would render.

Pair No identity at all The first screen anyone ever sees carries no logo and no wordmark. Sign-in, two screens later, does.
Pair A keyboard for 8 characters On a landscape tablet the soft keyboard covers roughly a third of the screen, and the layout is vertically centred, so the field moves as it opens.
Pair Nowhere to find the code The instruction names a dashboard without saying where in it to look, and there is no way to paste a code that arrived in a message.
Prepare A title that is a noun “This tablet” names the screen instead of saying what to do on it.
Prepare No way back to pairing Nothing in the app unpairs a device. A rented tablet paired to the wrong account is a dead end that needs a reinstall.
Sign in The instruction is dropped “Who is on the door?” is hidden on compact tablets — removed exactly where the screen is hardest to read.

Where do I find this code?
  • 1
    The wordmark, first Great Vibes “Fancy”, the same mark sign-in already uses. The first screen should be the most identifiable one, not the only anonymous one.
  • 2
    A step rail Setup is three screens and nothing said so. Someone who stops halfway has no idea whether they finished.
  • 3
    Eight boxes, not a field Each character gets its own target, a mistyped one is visible without re-reading, and the group is 30 % of the screen wide instead of a thin line. The 4–4 break matches how codes are read aloud.
  • 4
    Paste Codes arrive in a message on someone's phone, or in an email on the tablet itself. Retyping eight characters is the failure mode, not the flow.
  • 5
    Where the code lives Expands to the three-step path through the dashboard. The current copy also still says “Fancy RSVP” — a leftover from the rebrand.
  • 6
    A reserved error slot Errors currently appear between the field and the button, so the button drops as you reach for it. The space is now always there.

What it would take

  • One new shared component. SetupHeader — wordmark plus step rail, used by all three screens. Roughly 60 lines.
  • One new control. CodeCells — the segmented entry, driven by the existing view-model string so PairViewModel is untouched.
  • One new capability. Unpair, in DeviceRepository plus a confirmation dialog. Everything else on these three screens is layout and copy.
  • Around a dozen strings. Including the stale pair_instructions, which still says “Fancy RSVP” after the rebrand.
  • No change to any view-model, repository, or network call other than unpair.

Not verified. There is no JDK on this machine, so nothing here has been compiled and no screen in this app has been seen rendered on a device. Treat the mockup as the design decision and the tablet as the test.
